## 7. Divi page content — section identification (no blind conversion performed)

Every one of the 73 pages uses Divi Builder shortcodes
(`et_pb_section`/`et_pb_row`/`et_pb_column` at minimum). Per your
instruction, I did **not** attempt any shortcode-to-HTML conversion —
only shortcode-tag *presence* detection, which is recorded per page in
`page-mapping.json`'s notes and per full detail in `wp-full-extract.json`.
Two categories worth calling out explicitly:

- **Two real form modules were found** (see §9 — Forms) — `csr-main`
  uses Divi's native `et_pb_contact_form` module; `csr-projects` and
  `careers` embed a **WPForms** plugin form via `[wpforms id="…"]`
  shortcode (form IDs `8780` and `13561` respectively). This corrects an
  impression from the earlier plain inventory pass, which found no
  form-plugin postmeta — the forms exist as inline shortcodes inside Divi
  content, not as separate exportable WordPress records.
- **Content that cannot be safely auto-transformed at all:** anything
  using `et_pb_slider`/`et_pb_fullwidth_slider` (image carousels),
  `et_pb_accordion` (the `audit-reports` page), `et_pb_toggle`/`et_pb_tabs`
  if present, and any page using `_et_pb_ab_subjects` (Divi's built-in
  A/B-testing feature — found in postmeta keys sitewide) — these all
  require a human to look at the rendered WordPress page directly and
  decide the equivalent new-site structure; there is no mechanical
  mapping from a shortcode name to this project's component set.

## 11. Recommended migration phases

Derived from what's actually confident vs. blocked above, not the generic
template — order follows what has the fewest open decisions first:

**Phase M1 — Credibility documents.** Lowest risk: destinations already
exist and are already partly wired. Resolve the 3 near-match filenames
(§5) and the 80G-Renewal duplicate-upload ambiguity, decide what (if
anything) happens to the 43 newsletter/activity-report PDFs and 9 job PDFs,
then wire the rest.

**Phase M2 — Blog dry-run.** Destination (`/media/blog`) exists and is
proven (this project's `BlogPost`/`BlogPostRevision` module is already
built and working). Needs: clean-slug decisions for encoded slugs,
resolution of the one suspicious title/slug overlap with existing demo
content, and new SEO metadata for the 16 posts that don't have Rank Math
data. Dry-run only, matching this project's own `import/` convention
(§ README).

**Phase M3 — Testimonials.** Small (13 items), destination for 7 of them
is clear (Home slider); the other 6 need one review decision. Low
technical risk once that decision is made.

**Phase M4 — Static structured pages (the 19 "A" pages).** Each needs a
human to open the live Divi page and manually re-author its content into
this project's existing page/section structure — no shortcuts, since
Divi content can't be safely auto-converted (§7).

**Phase M5 — Duplicate cluster resolution + the 27 "F" pages.** These
require your decisions before any technical work: which page in each
cluster is authoritative, and where (if anywhere) each F-page belongs —
including the real product decision on whether Credibility needs a new
"Audit Reports" section.

**Phase M6 — Forms rebuild.** Only 2 real forms (§9) — inspect their
actual fields in WordPress Admin, rebuild in the new Forms system. Small
but blocked on manual WordPress-admin inspection, so it can run in
parallel with M4/M5 rather than after them.

**Phase M7 — Media/S3.** Blocked entirely on D6 (AWS/S3 access, per the
existing Week 5 plan) — nothing here can start until that lands, but the
1,412-item inventory (§6) is already usable to plan the upload once it
does.

**Phase M8 — WPCode/global script parity.** Needs your manual checklist
answers (§8) before an equivalent can even be scoped, let alone built.

**Phase M9 — Redirects/SEO validation.** Deliberately last: redirects
depend on every duplicate-cluster and F-page decision above being final,
otherwise a redirect gets created to a target that later changes.

**Phase M10 — Final delta migration before launch.** Whatever changed on
the live WordPress site between this export and go-live (this export is a
snapshot from 2026-09-29) — re-run the same read-only inventory process
against a fresh export just before cutover and diff it against this one.
